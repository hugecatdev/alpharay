# AlphaRay — бэкенд

FastAPI-сервис умного кредитного кабинета на PostgreSQL: авторизация, заявки и кредитный конвейер, проверки по ЕГРЮЛ/ФНС/БКИ и счетам в банке (синтетические источники за заменяемым шлюзом), скоринг и кредитные правила, кабинет андеррайтера, администрирование банка (кредитная политика, продукты, сотрудники, распределение, аудит), уведомления, договор и график платежей, ИИ-ассистент Рэй. Контракт API — `frontend/src/api/types.ts` и `docs/api/openapi.json`; Swagger UI — `/api/docs`.

## Запуск

Весь проект в Docker — из корня репозитория: `docker compose up --build`, кабинет на `http://localhost:8080`. Поднимаются PostgreSQL 17, API, отдельный воркер конвейера и фронтенд.

Локально нужен PostgreSQL. Проще всего — контейнер:

```bash
docker run -d --name alpharay-db -e POSTGRES_USER=alpharay -e POSTGRES_PASSWORD=alpharay \
  -e POSTGRES_DB=alpharay -p 127.0.0.1:5432:5432 postgres:17.6-alpine3.22
python3 -m venv .venv
.venv/bin/pip install poetry==2.5.1
.venv/bin/poetry sync
cp .env.example .env
.venv/bin/uvicorn app.main:app --reload --port 8000
```

При старте сервис сам создаёт базу (если её нет), применяет миграции Alembic и, если таблица пользователей пуста, загружает демо-данные. Миграции и посев идут под advisory-блокировкой PostgreSQL, поэтому несколько экземпляров API и воркер стартуют одновременно без гонок. Локально воркер конвейера работает в процессе API (`PIPELINE_WORKER=true`), в Docker — отдельным контейнером `worker` (`python -m app.worker`).

Фронтенд в `npm run dev` проксирует `/api` на `http://localhost:8000`.

Служебные команды:

```bash
.venv/bin/python -m app.cli migrate        # миграции и посев, если база пустая
.venv/bin/python -m app.cli reset-demo     # очистить все таблицы и заново загрузить демо-данные
docker compose exec backend python -m app.cli reset-demo
```

## Хранилище

PostgreSQL 17, SQLAlchemy 2.1 (ORM, драйвер psycopg 3), миграции — Alembic (`migrations/versions`). Время хранится как `timestamptz` в UTC, деньги — целыми рублями (`BIGINT`), ставки — `NUMERIC(6,3)`, снимки продукта, компании и финансовых данных — `JSONB`. Модель — `app/models.py`, запросы — `app/repo.py`.

| Таблицы | Что хранят |
|---|---|
| `users`, `companies` | учётки (пароль — PBKDF2-хеш) и компании-клиенты |
| `company_sources`, `account_turnover`, `external_loans` | синтетические данные внешних систем: ЕГРЮЛ/ЕГРИП, ФНС, БКИ, обороты по счёту, кредиты в других банках |
| `products`, `credit_policies` | каталог (с версией продукта) и кредитная политика — каждое изменение сохраняется новой версией |
| `applications` | заявка: статус, текущие параметры, версия для `If-Match`, номер ревизии, время следующего шага конвейера |
| `application_revisions` | неизменяемые снимки анкеты: при отправке и при каждом ответе на запрос банка |
| `check_results` | результат каждой проверки по ревизии: источник, статус `OK`/`ISSUES`/`ERROR`, попытка, ответ |
| `risk_assessments`, `credit_decisions` | оценка риска (балл, грейд, факторы, версия модели и политики) и решения с кодами причин — отдельно |
| `info_requests` | все запросы информации с ответами и ссылкой на ревизию ответа |
| `offers`, `contracts`, `disbursements` | версии предложений и их принятие, договор и подпись, выдача (одна на заявку, уникальный номер операции) |
| `application_events`, `notifications`, `audit_log`, `application_notes` | история переходов с `correlation_id`, уведомления, журнал действий банка, заметки андеррайтера |
| `assistant_sessions`, `assistant_messages` | диалоги с Рэем |

Номера заявок и операций выдачи — последовательности PostgreSQL. Данные переживают перезапуск контейнеров (том `postgres-data`); `docker compose down -v` удаляет тома и сбрасывает демо.

## Конвейер и воркер

Отправка заявки создаёт ревизию 1 и ставит заявку в очередь: у неё есть `next_run_at`. Воркер выбирает созревшие заявки запросом `SELECT … FOR UPDATE SKIP LOCKED`, каждую — в своей транзакции, поэтому несколько воркеров не берут одну заявку дважды, а команды клиента и банка, которые блокируют ту же строку, не сталкиваются с конвейером. Этапы по 2 секунды: `SUBMITTED → VALIDATING → ENRICHING → SCORING → DECIDING → решение`. Время перехода считается от входа в этап, поэтому история после простоя воркера такая же, как при непрерывной работе. Если шаг упал, его транзакция откатывается до savepoint, а заявка откладывается с экспоненциальной задержкой до минуты.

- `VALIDATING` — проверка полноты (`check_results`, тип `COMPLETENESS`).
- `ENRICHING` — шлюз источников `app/integrations.py`: ЕГРЮЛ/ЕГРИП, ФНС, счета в банке и БКИ. Шлюз — протокол `SourceGateway`, синтетическая реализация заменяется на реальные адаптеры без правки правил. Технический сбой БКИ — это `ERROR`, а не отрицательный факт: до 3 попыток через 2 секунды, затем ручное рассмотрение с кодом `INTEGRATION_ERROR`, а не отказ. Сбой моделируется параметром `POST /applications/:id/submit?mock_fail=`: `1` — БКИ не ответило один раз, повтор успешен; `2` — БКИ недоступно на всех попытках.
- `SCORING` — оценка риска по 7 факторам, стоп-факторы, рекомендация для андеррайтера.
- `DECIDING` — кредитные правила (ниже).

Предложение действует `offer_valid_days` дней: по истечении воркер переводит заявку в `EXPIRED`, а принять просроченное предложение нельзя (`409 OFFER_EXPIRED`). После подписания при `auto_disbursement=true` воркер через 3 секунды выдаёт кредит: создаётся запись в `disbursements` с номером операции `PAY-ГГГГММДД-NNNNNN`, договором и счётом. Выдача смоделирована (`simulated: true`), реальный платёж не проводится.

Переходы статусов заданы таблицей `TRANSITIONS` в `app/pipeline.py`; переход вне таблицы — `TransitionError` → `409 INVALID_TRANSITION`. Путь до выдачи: `APPROVED`/`COUNTER_OFFER` → `POST /offer/accept` (`OFFER_ACCEPTED`, создаётся договор) → `POST /sign` (`SIGNING`) → `POST /sign/kep` или `/sign/confirm` (`SIGNED`) → `DISBURSED`. Отозвать заявку можно до подписания; после отказа, отклонения, отзыва или истечения — `POST /applications/:id/resubmit` создаёт новый черновик со ссылкой на прежнюю заявку (`previous_application_id`), старое решение не меняется.

## Кредитные правила

Решение принимает `app/decision.py` по данным проверок, ревизии анкеты и кредитной политики — одинаково для демо-компаний и любых новых. Правила по порядку:

| № | Правило | Исход | Код |
|---|---|---|---|
| 1 | стоп-факторы: недействующая компания, налоговый долг, блокировки, просрочка > 90 дней, дисквалификация, массовый адрес | отказ или ручное (`stop_factors_decision`) | `STOP_FACTORS` |
| 2 | бизнес моложе `min_business_age_months` | отказ | `BUSINESS_TOO_YOUNG` |
| 3 | выручка в анкете расходится с ФНС больше чем на `revenue_mismatch_percent` % | запрос выручки и выписки; после ответа — проверка по оборотам счёта, не сходится — ручное | `REVENUE_MISMATCH`, `REVENUE_UNCONFIRMED` |
| 4 | сумма выше порога (`manual_review_amount_threshold` или порог продукта) | ручное | `AMOUNT_ABOVE_THRESHOLD` |
| 5 | просрочка за 24 мес. больше `manual_review_overdue_days` | ручное | `OVERDUE_HISTORY` |
| 6 | все платежи по кредитам с новым больше `max_debt_load` денежного потока | встречное предложение на наибольшую посильную сумму с пересчётом скоринга, иначе отказ | `DEBT_LOAD_LIMIT`, `HIGH_DEBT_LOAD`, `NO_CASH_FLOW` |
| 7 | грейд скоринга по политике: A/B — одобрение с надбавкой, C — ручное, D — отказ | по политике | `AUTO_APPROVED`, `RISK_MARKUP`, `BORDERLINE_SCORE`, `LOW_SCORE`, `POLICY_COUNTER_OFFER` |
| — | БКИ не ответило после 3 попыток | ручное | `INTEGRATION_ERROR` |

Коды причин видят андеррайтер и API банка; клиенту показываются только формулировки. Денежный поток для правила 6 — по оборотам счёта (чистый поток + текущие платежи), а для компании без счёта — по анкете: `(выручка − расходы) / 12 + текущие платежи`.

Демо-компании ведут себя так из-за своих данных, а не из-за особых веток кода (`frontend/DEMO_ACCOUNTS.txt`): у client2 бизнесу 8 месяцев и маленький поток — 2 млн на 12 мес. не проходят по нагрузке, правило 6 предлагает 950 000 ₽; у client3 просрочка 45 дней — правило 5; у client4 налоговый долг, блокировки и просрочка 203 дня — правило 1; у client5 выручка по ФНС на 26% ниже оборотов — правило 3.

**Кредитная политика** (`GET/PUT /admin/policy`, версии в `credit_policies`) отделяет скоринг от решения: скоринг даёт балл и грейд, политика — что с ним делать.

- `grades.{A,B,C,D}` — минимальный балл грейда, авторешение (`APPROVED`, `COUNTER_OFFER`, `MANUAL_REVIEW`, `REJECTED`) и надбавка к ставке продукта.
- `manual_review_amount_threshold` и `product_review_thresholds` — выше порога заявка уходит специалисту.
- `stop_factors_decision` — отказ или ручное рассмотрение при стоп-факторах.
- `max_debt_load` (0,7), `revenue_mismatch_percent` (20), `manual_review_overdue_days` (30), `min_business_age_months` (3) — пороги правил 2–6.
- `counter_offer_share` — доля суммы во встречном предложении по политике грейда, `offer_valid_days` — срок действия предложения.
- `manual_review_sla_hours` — SLA для дашборда, `auto_assign` — распределять ручные заявки на наименее загруженного андеррайтера, `auto_disbursement` — выдавать автоматически после подписания или ждать подтверждения банка.

Решение и оценка риска хранят версию политики и модели, на которых получены.

## Надёжность API

- **Транзакции.** Каждый запрос — одна транзакция; commit выполняется до отправки ответа (зависимость `get_db` со `scope="function"`). Команды блокируют строку заявки `SELECT … FOR UPDATE`, поэтому отзыв одновременно с работой конвейера даёт один согласованный результат.
- **Идемпотентность.** Команды (`POST /applications`, `submit`, `cancel`, `resubmit`, `info-requests/:id/respond`, `offer/accept`, `offer/decline`, `sign`, `sign/confirm`, `sign/kep`, банковские `decision` и `disburse`) принимают заголовок `Idempotency-Key`. Повтор с тем же ключом и тем же запросом возвращает сохранённый ответ с заголовком `Idempotent-Replayed: true`; тот же ключ с другим запросом — `422 IDEMPOTENCY_KEY_REUSED`. Фронтенд отправляет ключ с каждой командой и при обрыве сети повторяет запрос с тем же ключом.
- **Версии.** `Application.version` растёт при каждом изменении; `GET` и `PATCH /applications/:id` отдают `ETag`. `PATCH` с `If-Match: "<версия>"` и устаревшей версией — `409 VERSION_CONFLICT`. Принятие предложения сверяет `offer_id` с актуальной версией условий — `409 OFFER_OUTDATED`.
- **Ошибки.** Единый формат `{ detail, code, missing?, field_errors?, correlation_id }`; конфликт данных в БД — `409 CONFLICT`, недоступность БД — `503 DATABASE_UNAVAILABLE`, лимит — `429 RATE_LIMITED` с `Retry-After`.

## Наблюдаемость

- Логи — JSON в stdout: время, уровень, логгер, сообщение, `correlation_id`, для HTTP — метод, путь, статус, длительность; для конвейера — `application_id` и попытка.
- `correlation_id` берётся из заголовка `X-Request-ID` или генерируется, возвращается в `X-Request-ID` и в теле ошибки, пишется в `application_events` и `audit_log` — сообщение из интерфейса сопоставляется с логом и историей заявки.
- `GET /api/health/live` — процесс жив. `GET /api/health/ready` — `database`, `migrations` (версия схемы совпадает с кодом), `pipeline` (самый старый просроченный шаг очереди моложе 30 с), `assistant` (`configured`/`disabled`, на готовность не влияет); БД недоступна — `503`. Healthcheck контейнера смотрит `ready`.

## Ассистент Рэй

Рэй — агент поверх OpenAI-совместимого Chat Completions с tool calling. Провайдер меняется тремя переменными: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` — без изменений кода.

- **Без ключа Рэй полностью скрыт**: `/api/config` отдаёт `assistant_enabled=false`, фронт не показывает панель и кнопки «?», весь сценарий проходит формами. Платные ресурсы для проверки решения не нужны.
- Если LLM не ответила или упала во время ответа — `503 ASSISTANT_UNAVAILABLE`, фронт пишет «Ассистент временно недоступен, все действия доступны в кабинете». Rule-based подмены нет.
- Системный промпт — `app/assistant/system_prompt.md`. Рэй объясняет и по прямой просьбе клиента подставляет сумму и срок на шаге «Сумма и срок»; не создаёт и не отправляет заявки, не принимает офферы, не обещает одобрение.
- Контекст (`app/assistant/prompt.py`): в системный промпт сервер кладёт сводку компании (чистый поток, предварительный лимит с расшифровкой, платежи по кредитам), открытую заявку, данные экрана, готовый расчёт платежа по экрану с вариантами «дольше срок» и «меньше сумма» и список элементов для подсветки с подписями. Цифры считает сервер, а не модель.
- Раунды (`app/assistant/agent.py`): в первом раунде модель вызывает `show_hints` и, если нужно, инструменты данных; во втором отвечает текстом. Если данных не хватило — ещё раунд, максимум `LLM_MAX_ROUNDS`, затем ответ запрашивается с `tool_choice=none`. Обычно 2–3 раунда и 1–3 с.
- Инструменты (`app/assistant/tools.py`): `get_application`, `list_applications`, `get_company_overview`, `list_products`, `calc_loan` — читают данные только своей компании, каждый вызов — короткая транзакция, во время запроса к LLM соединение с БД не держится; `show_hints` — подсветка 0–2 элементов экрана и 2–3 чипа следующих вопросов; `fill_loan_form` — подставить сумму и/или срок, только на экране `wizard.amount` и в пределах продукта. Служебные коды в данных экрана заменяются названиями, а в ответе — вычищаются (`app/assistant/humanize.py`).
- На `429/5xx` с `Retry-After` до 8 с, на обрыв соединения и на некорректный вызов инструмента (`tool_use_failed`) — повтор.

Провайдеры:

| Провайдер | `LLM_BASE_URL` | `LLM_MODEL` | Ключ |
|---|---|---|---|
| Groq (бесплатный тариф) | `https://api.groq.com/openai/v1` | `openai/gpt-oss-120b` | `gsk_…` с console.groq.com |
| Ollama в compose (`--profile ollama`) | `http://ollama:11434/v1` | `qwen3:8b` | любая непустая строка, например `ollama` |
| Ollama локально | `http://localhost:11434/v1` | `qwen3:8b` | любая непустая строка |
| vLLM / cloud.ru Foundation Models / другое | URL до `/v1` | имя модели провайдера | ключ провайдера |

У бесплатного тарифа Groq лимит 8 000 токенов в минуту на модель; один вопрос — 2–3 раунда по ~2 000–3 500 токенов, то есть 1–2 вопроса в минуту. При частых вопросах подряд Groq отвечает 429; если `Retry-After` не больше 8 с, Рэй ждёт и повторяет, иначе сообщает о недоступности.

## Сторона банка: роли и администрирование

| Роль | Учётка (пароль `demo`) | Что может |
|---|---|---|
| `UNDERWRITER` — кредитный аналитик | `underwriter@bank.local`, `underwriter2@bank.local` | очередь, карточка заявки с проверками и версиями анкеты, взять в работу, решение (одобрить / другие условия / запросить информацию / отказать), внутренние заметки, подтверждение выдачи |
| `ADMIN` — руководитель кредитного управления | `admin@bank.local` | всё, что андеррайтер, плюс `/api/admin/*` |

`/api/bank/*` доступен обеим ролям, `/api/admin/*` — только `ADMIN`. Заблокированный сотрудник не может войти (`403 ACCOUNT_DISABLED`), его токены перестают работать, а его незакрытые заявки возвращаются в общую очередь.

| Эндпоинт | Назначение |
|---|---|
| `GET /admin/dashboard?days=` | KPI конвейера: заявки по статусам, выдано, доля одобрений и авторешений, время до решения, время ручного рассмотрения, воронка, разрез по продуктам и андеррайтерам, нарушения SLA |
| `GET /admin/applications?status=&product_code=&assignee_id=&sla_breached=&q=` | все заявки с исполнителем, временем ожидания и флагом SLA; `assignee_id=none` — без исполнителя, `q` — номер, компания или ИНН |
| `POST /admin/applications/{id}/assign` `{assignee_id}` | назначить андеррайтера или вернуть в общую очередь (`null`) |
| `GET/POST /admin/staff`, `PATCH /admin/staff/{id}` | сотрудники банка: завести, сменить роль или должность, сбросить пароль, заблокировать |
| `GET/POST /admin/products`, `PATCH /admin/products/{code}` | каталог: ставки, лимиты, сроки, цели, счёт поставщика, группа, обеспечение, целевое использование, отрасли по ОКВЭД, доступность. Отключённый продукт пропадает из `/config`, по нему нельзя создать или отправить заявку; условия уже созданных заявок не меняются — заявка хранит снимок продукта |
| `GET/PUT /admin/policy` | кредитная политика, каждое изменение — новая версия |
| `GET /admin/audit?entity_type=&entity_id=&actor_id=&action=&limit=` | журнал действий банка: решения, назначения, заметки, выдачи, изменения продуктов, политики и сотрудников |
| `GET/POST /bank/applications/{id}/notes` | внутренние заметки андеррайтера, клиенту не видны |
| `POST /bank/applications/{id}/disburse` | подтвердить выдачу по подписанному договору |

Клиент видит конвейер крупно: `GET /applications/{id}/events` не отдаёт внутренние этапы `VALIDATING`, `ENRICHING`, `SCORING`, `DECIDING`, повторные запросы в БКИ, ФИО сотрудников банка и внутреннюю причину ручного рассмотрения; `decision.made_by` для клиента — `SYSTEM` или «Специалист банка», коды причин и решение типа `MANUAL_REVIEW` клиенту не показываются. Полная история с исполнителями — в `/bank/applications/{id}/events`; карточка банка (`BankApplication`) дополнительно содержит `checks`, `revisions` и `info_requests`.

## Нагрузка, лимит и продукты

- Чистый поток — среднее «поступления минус списания» по счёту за 12 месяцев; платежи по текущим кредитам уже входят в списания. Поток до платежей = чистый поток + текущие платежи.
- Долговая нагрузка — все платежи по кредитам вместе с новым к потоку до платежей: до 40% — комфортно, 40–70% — заметно, больше 70% — встречное предложение или отказ. По этой формуле считают главная, мастер заявки, Рэй и правило 6.
- Предварительный лимит (`insights.pre_approved_limit`) — наибольшая сумма на 24 мес. по ставке оборотного кредита, при которой все платежи укладываются в 40% потока до платежей; при стоп-факторах лимита нет. У андеррайтера отдельная метрика «Платежи к выручке».
- `Product.repayment`: `ANNUITY` — равные платежи; `REVOLVING` — овердрафт: проценты только на использованную сумму, долг гасится поступлениями, графика нет (`GET /schedule` → `[]`), `offer.monthly_payment` — проценты за месяц при полном использовании лимита, договор — об овердрафтном кредитовании.
- `Product.down_payment_share` — минимальный собственный аванс; у кредита на оборудование и лизинга 10%, оборудование в залоге. Мастер и договор показывают сумму аванса и стоимость оборудования.

## Проверки

Тесты работают с настоящим PostgreSQL: схема мигрируется один раз за прогон, перед каждым тестом таблицы очищаются и заново засеваются, часы управляемые, конвейер продвигается явным вызовом воркера.

```bash
docker run -d --name alpharay-test-pg -e POSTGRES_PASSWORD=test -p 127.0.0.1:55432:5432 postgres:17.6-alpine3.22
.venv/bin/ruff check app tests migrations
.venv/bin/ruff format --check app tests migrations
.venv/bin/pytest                                      # TEST_DATABASE_URL переопределяет адрес тестовой базы
.venv/bin/alembic check                               # модели совпадают с миграциями
```

По умолчанию тесты подключаются к `postgresql+psycopg://postgres:test@127.0.0.1:55432/alpharay_test` и сами создают базу. Покрыты сценарии client1–client6, андеррайтера, администратора и агента Рэя на фейковом LLM, а также истечение и версии предложений, идемпотентность, единственная выдача, `If-Match`, повторная подача, запрет недопустимых переходов, сбой и недоступность БКИ, `SKIP LOCKED`, сохранность данных после перезапуска, health, лимиты и `X-Request-ID`. E2E фронтенда (`npm run e2e`) сами стартуют этот бэкенд с базой `alpharay_e2e` в том же PostgreSQL.
