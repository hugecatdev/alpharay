# AlphaRay — бэкенд

FastAPI-сервис умного кредитного кабинета: авторизация, заявки и кредитный конвейер, обогащение из ЕГРЮЛ/ФНС/БКИ (синтетические данные), скоринг, кабинет андеррайтера, администрирование банка (кредитная политика, продукты, сотрудники, распределение, аудит), уведомления, договор и график платежей, ИИ-ассистент Рэй. Контракт API — `frontend/src/api/types.ts` и `docs/api/openapi.json`; Swagger UI — `/api/docs`.

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install poetry==2.5.1
.venv/bin/poetry sync
cp .env.example .env
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Фронтенд в `npm run dev` проксирует `/api` на `http://localhost:8000`.

Весь проект в Docker — из корня репозитория: `docker compose up --build`, кабинет на `http://localhost:8080`.

## Ассистент Рэй

Рэй — агент поверх OpenAI-совместимого Chat Completions с tool calling. Провайдер меняется тремя переменными: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` — без изменений кода.

- **Без ключа Рэй полностью скрыт**: `/api/config` отдаёт `assistant_enabled=false`, фронт не показывает панель и кнопки «?», весь сценарий проходит формами. Платные ресурсы для проверки решения не нужны.
- Если LLM не ответила или упала во время ответа — `503 ASSISTANT_UNAVAILABLE`, фронт пишет «Ассистент временно недоступен, все действия доступны в кабинете». Rule-based подмены нет.
- Системный промпт — `app/assistant/system_prompt.md`. Рэй объясняет и по прямой просьбе клиента подставляет сумму и срок на шаге «Сумма и срок»; не создаёт и не отправляет заявки, не принимает офферы, не обещает одобрение.
- Контекст (`app/assistant/prompt.py`): в системный промпт сервер кладёт сводку компании (чистый поток, предварительный лимит с расшифровкой, платежи по кредитам), открытую заявку, данные экрана, готовый расчёт платежа по экрану с вариантами «дольше срок» и «меньше сумма» и список элементов для подсветки с подписями. Цифры считает сервер, а не модель.
- Раунды (`app/assistant/agent.py`): в первом раунде модель вызывает `show_hints` и, если нужно, инструменты данных; во втором отвечает текстом. Если данных не хватило — ещё раунд, максимум `LLM_MAX_ROUNDS`, затем ответ запрашивается с `tool_choice=none`. Обычно 2–3 раунда и 1–3 с.
- Инструменты (`app/assistant/tools.py`): `get_application`, `list_applications`, `get_company_overview`, `list_products`, `calc_loan` — читают данные только своей компании; `show_hints` — подсветка 0–2 элементов экрана (`hints`, цели проверяются по списку экрана) и 2–3 чипа следующих вопросов (`suggestions`); `fill_loan_form` — подставить сумму и/или срок (`actions: set_loan_params`), только на экране `wizard.amount` и в пределах продукта. Если модель продублировала вопросы в тексте, сервер их вырезает; служебные коды (`EQUIPMENT`, `DRAFT`, `revenue_12m`…) в данных экрана заменяются названиями, а в ответе — вычищаются (`app/assistant/humanize.py`).
- На `429/5xx` с `Retry-After` до 8 с, на обрыв соединения и на некорректный вызов инструмента (`tool_use_failed`) — повтор.

Провайдеры:

| Провайдер | `LLM_BASE_URL` | `LLM_MODEL` | Ключ |
|---|---|---|---|
| Groq (бесплатный тариф) | `https://api.groq.com/openai/v1` | `openai/gpt-oss-120b` | `gsk_…` с console.groq.com |
| Ollama в compose (`--profile ollama`) | `http://ollama:11434/v1` | `qwen3:8b` | любая непустая строка, например `ollama` |
| Ollama локально | `http://localhost:11434/v1` | `qwen3:8b` | любая непустая строка |
| vLLM / cloud.ru Foundation Models / другое | URL до `/v1` | имя модели провайдера | ключ провайдера |

У бесплатного тарифа Groq лимит 8 000 токенов в минуту на модель; один вопрос — 2–3 раунда по ~2 000 токенов, то есть 1–2 вопроса в минуту. При частых вопросах подряд Groq отвечает 429, Рэй ждёт `Retry-After` и повторяет, а если лимит не освободился — сообщает о недоступности. Требование организаторов: интеграция совместима с OpenAI API, base URL, ключ и модель заменяемы, проверка не зависит от платных ресурсов — эксперты подключают своего провайдера переменными выше.

## Сторона банка: роли и администрирование

| Роль | Учётка (пароль `demo`) | Что может |
|---|---|---|
| `UNDERWRITER` — кредитный аналитик | `underwriter@bank.local`, `underwriter2@bank.local` | очередь, карточка заявки, взять в работу, решение (одобрить / другие условия / запросить информацию / отказать), внутренние заметки, подтверждение выдачи |
| `ADMIN` — руководитель кредитного управления | `admin@bank.local` | всё, что андеррайтер, плюс `/api/admin/*` |

`/api/bank/*` доступен обеим ролям, `/api/admin/*` — только `ADMIN`. Заблокированный сотрудник не может войти (`403 ACCOUNT_DISABLED`), его токены перестают работать, а его незакрытые заявки возвращаются в общую очередь.

| Эндпоинт | Назначение |
|---|---|
| `GET /admin/dashboard?days=` | KPI конвейера: заявки по статусам, выдано, доля одобрений и авторешений, время до решения, время ручного рассмотрения, воронка, разрез по продуктам и андеррайтерам, нарушения SLA |
| `GET /admin/applications?status=&product_code=&assignee_id=&sla_breached=&q=` | все заявки с исполнителем, временем ожидания и флагом SLA; `assignee_id=none` — без исполнителя, `q` — номер, компания или ИНН |
| `POST /admin/applications/{id}/assign` `{assignee_id}` | назначить андеррайтера или вернуть в общую очередь (`null`) |
| `GET/POST /admin/staff`, `PATCH /admin/staff/{id}` | сотрудники банка: завести, сменить роль или должность, сбросить пароль, заблокировать |
| `GET/POST /admin/products`, `PATCH /admin/products/{code}` | каталог: ставки, лимиты, сроки, цели, счёт поставщика, группа, обеспечение, целевое использование, отрасли по ОКВЭД, доступность. Отключённый продукт пропадает из `/config`, по нему нельзя создать или отправить заявку; условия уже созданных заявок не меняются |
| `GET/PUT /admin/policy` | кредитная политика (ниже) |
| `GET /admin/audit?entity_type=&entity_id=&actor_id=&action=&limit=` | журнал действий банка: решения, назначения, заметки, выдачи, изменения продуктов, политики и сотрудников |
| `GET/POST /bank/applications/{id}/notes` | внутренние заметки андеррайтера, клиенту не видны |
| `POST /bank/applications/{id}/disburse` | подтвердить выдачу по подписанному договору |

**Кредитная политика** (`app/models.py:default_policy`, правится через `PUT /admin/policy`) отделяет скоринг от решения, как требует кейс: скоринг даёт балл и грейд, политика — что с ним делать.

- `grades.{A,B,C,D}` — минимальный балл грейда, авторешение (`APPROVED`, `COUNTER_OFFER`, `MANUAL_REVIEW`, `REJECTED`) и надбавка к ставке продукта. Одинаковый грейд даёт разные условия на разных продуктах — от базовой ставки продукта.
- `manual_review_amount_threshold` и `product_review_thresholds` — выше порога заявка уходит специалисту.
- `stop_factors_decision` — отказ или ручное рассмотрение при стоп-факторах ФНС/БКИ.
- `counter_offer_share` — доля суммы во встречном предложении, `offer_valid_days` — срок действия предложения.
- `manual_review_sla_hours` — SLA для дашборда, `auto_assign` — распределять ручные заявки на наименее загруженного андеррайтера, `auto_disbursement` — выдавать автоматически после подписания или ждать подтверждения банка.

По умолчанию политика повторяет прежнюю логику. Для пяти демо-компаний исход зафиксирован сценарием (см. `frontend/DEMO_ACCOUNTS.txt`), от политики у них зависят порог ручного рассмотрения client1, срок предложения, распределение и выдача. Остальные заявки — фоновые компании и онбординг client6 — решаются полностью по политике.

## Конвейер

Ленивый, по таймстемпам: каждый запрос продвигает заявки, у которых истекло время этапа (`SUBMITTED → VALIDATING → ENRICHING → SCORING → DECIDING` по 2 с, решение, `SIGNED → DISBURSED` через 3 с). Исходы для демо-компаний детерминированы (см. `frontend/DEMO_ACCOUNTS.txt`), для остальных — по скорингу. `?mock_fail=1` при `submit` эмулирует сбой БКИ: этап «Запрос данных» длится 6 с, повторный запрос в БКИ виден в истории у андеррайтера.

Клиент видит конвейер крупно: `GET /applications/{id}/events` не отдаёт внутренние этапы `VALIDATING`, `ENRICHING`, `SCORING`, `DECIDING`, ФИО сотрудников банка и внутреннюю причину ручного рассмотрения; `decision.made_by` для клиента — `SYSTEM` (автоматическое решение) или «Специалист банка», решение типа `MANUAL_REVIEW` клиенту не показывается. Уведомление о ходе рассмотрения одно — когда заявка ушла на проверку. Полная история с исполнителями — в `/bank/applications/{id}/events`. Причины автоматического одобрения формулируются языком клиента по сильным факторам скоринга.

## Нагрузка, лимит и продукты

- Чистый поток — среднее «поступления минус списания» по счёту за 12 месяцев; платежи по текущим кредитам уже входят в списания. Поток до платежей = чистый поток + текущие платежи.
- Долговая нагрузка — все платежи по кредитам вместе с новым к потоку до платежей: до 40% — комфортно, 40–70% — заметно, больше 70% — высокий риск. По этой формуле считают главная, мастер заявки и Рэй.
- Предварительный лимит (`insights.pre_approved_limit`) — наибольшая сумма на 24 мес. по ставке оборотного кредита, при которой все платежи укладываются в 40% потока до платежей; при стоп-факторах лимита нет. У андеррайтера отдельная метрика «Платежи к выручке».
- `Product.repayment`: `ANNUITY` — равные платежи; `REVOLVING` — овердрафт: проценты только на использованную сумму, долг гасится поступлениями, графика нет (`GET /schedule` → `[]`), `offer.monthly_payment` — проценты за месяц при полном использовании лимита, договор — об овердрафтном кредитовании.
- `Product.down_payment_share` — минимальный собственный аванс; у кредита на оборудование и лизинга 10%, оборудование в залоге. Мастер и договор показывают сумму аванса и стоимость оборудования.

## Проверки

```bash
.venv/bin/ruff check app tests
.venv/bin/ruff format --check app tests
.venv/bin/pytest
```

Тесты поднимают приложение в памяти с управляемыми часами и проходят сценарии client1–client6, андеррайтера и агента Рэя на фейковом LLM. E2E фронтенда (`npm run e2e`) сами стартуют этот бэкенд.
